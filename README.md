# M5 Demand Forecast Agent — 대규모 실데이터 수요예측 + 자연어 설명 에이전트

> 2026-09-16 착수. `demand_forecasting_gbm`이 "정직한 범위"에 스스로 남긴 한계 —
> "실데이터 검증은 단일 월별 시리즈(204건)뿐이다, 다품목 실데이터로는 검증하지 못했다" —
> 를 정면으로 메우는 후속 프로젝트. 여러 세션에 걸쳐 진행(예상 규모: 수 주~두 달).

## 목표·이유

`demand_forecasting_gbm`의 실데이터 검증은 단일 월별 시계열(204건) 하나뿐이었고, "여러 매장/
품목에서 배우는" 그래디언트 부스팅의 장점이 발휘될 조건이 아니었다. Kaggle **M5 Forecasting -
Accuracy**(월마트 판매 데이터, 3,049개 품목 × 10개 매장 = 30,490개 일별 시계열, 2011-01-29 ~
2016-06-19, 캘린더·이벤트·SNAP 지원·가격 포함)로 이 질문에 실제 규모에서 답한다: "시리즈가
충분히 많아지면 GBM의 교차 시리즈 학습 우위가 실제로 나타나는가?"

여기에 지금까지 만든 RAG·에이전트 스택(TechDocRAG·Inspection Copilot)을 얹어, 예측 결과를
자연어로 질의응답하는 설명 에이전트를 붙인다. "AI Agent & Forecasting"을 함께 요구하는 채용
공고(캐롯아이 등)가 늘고 있는데, 지금까지는 이 둘을 각각 다른 프로젝트로 증명했지 한 시스템
안에서 결합해 보인 적이 없다.

## 상품성

- 수요예측은 재고·인력·마케팅 예산 배분에 바로 쓰이는 실무 문제. M5는 이 문제의 업계 표준
  벤치마크(원 대회는 Uber·Walmart·Amazon 등 실무자가 대거 참가)라 "내 모델이 실무 기준으로
  어느 수준인가"를 외부 검증된 지표(WRMSSE, 공식 리더보드)로 말할 수 있다.
- 자연어 설명 에이전트는 "예측 수치를 보여준다"에서 "왜 그 수치가 나왔는지 근거를 설명한다"로
  한 단계 나아간 것 — 가격 변화·SNAP 지원일·최근 추세 같은 근거를 사람이 확인할 수 있는 형태로
  내놓는다는 점에서, 이 프로젝트 전체가 반복해 온 "LLM 출력을 사람이 아니라 근거로 재검증한다"는
  습관과 같은 축이다.

## 모델링 채용 근거

- **LightGBM/XGBoost 다품목 학습**: `demand_forecasting_gbm`에서 이미 업계 표준으로 확인한
  스택을 그대로 쓰되, 이번엔 30,490개 시계열을 하나의 학습셋으로 묶어 교차 시리즈 학습이 실제로
  작동하는지를 직접 확인하는 것이 핵심 실험이다.
- **계층적 집계 비교(전체→state→store→category→item)**: M5는 공식적으로 12개 집계 레벨의
  WRMSSE로 채점한다 — 개별 품목 단위 예측만이 아니라 집계 단위에서의 정확도까지 함께 본다.
- **가드레일 에이전트(설명 레이어)**: LangGraph 기반으로, 자연어 질의 → 예측 조회 도구 호출 →
  근거(가격·이벤트·SNAP·추세) 조회 도구 호출 → 답변 생성의 흐름을 만든다. Inspection Copilot에서
  이미 검증한 "도구 스키마 + 서버 재검증" 패턴을 재사용한다.

## 성능 비교 (진행 중 — 채워 나감)

공식 검증 구간(train ≤ d_1913, forecast d_1914~1941, 28일) 기준. 학습 구간 마지막 28일
(d_1886~1913) 달러 매출 비중으로 가중, 12개 레벨 균등평균(1/12) — M5 공식 정의 그대로.

| 모델 | WRMSSE(overall) | item_store(최하위) | total(최상위) |
|---|---:|---:|---:|
| seasonal-naive(7일 전 반복) | **0.9128** | 1.3051 | 0.7514 |
| LightGBM(재귀적 28일 예측) | 0.9601 | **1.0039** | 0.8555 |
| LightGBM(직접·180일·L2, 최고 기록) | 0.9200 | 1.0238 | 0.8089 |
| LightGBM(직접·180일·Tweedie) | 0.9374 | 1.0232 | 0.8718 |
| LightGBM(직접·전체이력·L2) | 0.9386 | 1.0235 | 0.8451 |

- 최하위 레벨(item_store, 1.3051)이 최상위 레벨(total, 0.7514)보다 훨씬 나쁘다 — 개별 품목 단위
  변동은 크지만 합산하면 상쇄된다는, 계층적 시계열의 전형적인 패턴이 그대로 나타났다.
- 참고용 눈대중: 공개된 M5 커뮤니티 기록상 단순 베이스라인은 대체로 0.8~1.1대, 상위권 솔루션은
  0.5대였다 — 우리 베이스라인 0.9128이 그 범위 안에 들어와 파이프라인 정합성의 근거가 된다.

### LightGBM이 전체적으로는 졌지만 레벨별로 갈렸다 (2026-09-16)

**LightGBM(전체 30,490시리즈 통합 학습, lag/rolling/가격/캘린더 특징, 재귀적 28일 예측)의 종합
WRMSSE(0.9601)는 naive(0.9128)보다 나쁘다.** `demand_forecasting_gbm`·`predictive_maintenance`
둘 다 겪은 "더 정교한 모델이 항상 이기지 않는다"는 패턴이 여기서도 반복됐다. 다만 레벨별로 뜯어
보면 방향이 완전히 갈린다:

| 레벨 | naive | LightGBM | 승자 |
|---|---:|---:|---|
| item_store(최하위, 30,490개) | 1.3051 | **1.0039** | LightGBM (23% 개선) |
| item(3,049개) | 1.1797 | **1.0283** | LightGBM |
| item_state(9,147개) | 1.2394 | **1.0008** | LightGBM |
| total(최상위) | **0.7514** | 0.8555 | naive |
| store | **0.7993** | 0.9087 | naive |
| category | **0.7620** | 0.9342 | naive |

**진단**: LightGBM은 세분화된(개별 품목×매장) 레벨에서는 naive를 확실히 이긴다 — 교차 시리즈
학습으로 개별 품목의 고유 패턴(가격 반응, 이벤트 반응)을 잡아내는 것으로 보인다. 그런데 이걸
위로 합산하면 오히려 naive보다 나빠진다. 원인 후보는 **재귀적 예측의 오차 누적**이다 — 28일을
하루씩 예측하면서 예측값을 다음날 lag로 다시 먹이다 보니, 개별 시리즈의 작은 편향이 위쪽으로
합산될 때 서로 상쇄되지 않고 누적되는 방향으로 쌓였을 가능성이 있다(naive는 매주 반복이라 이런
누적 편향이 구조적으로 없다).

### 재귀 제거(direct multi-horizon)로 가설 검증 — 방향은 맞았지만 완전히 못 이겼다 (2026-09-16)

가설을 검증하려고 재귀 대신 **지평선(h=1~28)마다 별도 모델**(`train_direct_multihorizon`)로
바꿨다. 각 모델은 `extra_shift=h-1`로 "h일 전까지만 보이는" 특징만 써서, 예측이 다음 날 예측에
전혀 의존하지 않는다 — 오차가 전파될 통로 자체를 없앴다.

| 레벨 | naive | 재귀 LightGBM | 직접(재귀 없음) LightGBM |
|---|---:|---:|---:|
| total(최상위) | **0.7514** | 0.8555 | 0.8089 |
| item_store(최하위) | 1.3051 | **1.0039** | 1.0238 |
| OVERALL | **0.9128** | 0.9601 | 0.9200 |

재귀를 없애자 상위 레벨(total 0.8555→0.8089)이 실제로 개선됐다 — **재귀 오차 누적 가설의 방향은
맞았다.** 다만 naive(0.7514)를 완전히 따라잡지는 못했고, 최하위 레벨은 오히려 소폭 나빠졌다
(1.0039→1.0238).

**혼입 변수(정직하게 밝힘)**: 직접 모델 28개를 전부 학습시키는 데 시간이 오래 걸려(모델당
특징공학+학습), 이번 실행은 **학습 구간을 최근 180일로 제한**했다. 재귀 모델은 전체 이력(약 5.2년,
1,913일)을 다 썼다 — 그래서 이 비교는 "재귀 vs 직접"만 순수하게 비교한 게 아니라 "재귀+전체이력
vs 직접+180일"이 섞여 있었다. 아래에서 이 혼입 변수를 실제로 제거해 봤다.

### 혼입 변수 제거 결과 — 데이터를 더 넣었더니 오히려 나빠졌다 (2026-09-16)

직접 모델을 전체 이력(5.2년)으로 재학습해 순수 비교를 완성했다. 그 과정에서 OOM(메모리 부족)으로
한 번 죽었는데, 원인은 특징공학에 안 쓰는 넓은 컬럼(문자열 `d`, `wm_yr_wk` 등)까지 실은 채 28번
반복하며 중간 프레임을 명시적으로 안 비운 것이었다 — `data_loader.py`에서 불필요 컬럼을 드롭하고
(`long_df` 메모리 5.7GB→2.0GB), `models_gbm.py`에 반복마다 `del`+`gc.collect()`를 추가해 해결
(naive 베이스라인 점수가 수정 전후 0.9128로 동일함을 재확인해 회귀 없음 검증).

| 모델 | 학습 데이터 | OVERALL | total(최상위) | item_store(최하위) |
|---|---|---:|---:|---:|
| seasonal-naive | - | **0.9128** | **0.7514** | 1.3051 |
| LightGBM 재귀 | 전체 5.2년 | 0.9601 | 0.8555 | 1.0039 |
| LightGBM 직접 | 최근 180일 | 0.9200 | 0.8089 | 1.0238 |
| LightGBM 직접 | 전체 5.2년 | 0.9386 | 0.8451 | 1.0235 |

**전체 이력으로 학습한 직접 모델(0.9386)이 180일만 쓴 모델(0.9200)보다 더 나쁘다** — 데이터를
10배 넘게 늘렸는데 결과가 나빠졌다. `demand_forecasting_gbm`(실데이터에서 GBM이 naive에 짐)·
`predictive_maintenance`(딥러닝이 항상 이기지 않음)에 이어 이 프로젝트에서 세 번째로 반복되는
"더 정교하게/많이 하는 게 항상 낫지 않다" 패턴이다. 유력한 원인은 **비정상성(non-stationarity)**
— 소매 수요 패턴이 5.2년 사이 바뀌었을 가능성이 높은데(상품 수명주기·매장 리모델링·소비 트렌드),
오래된 데이터가 최근 패턴 학습에 잡음으로 작용했을 수 있다.

### Tweedie objective 시도 — M5 대회의 유명한 트릭인데도 더 나빠졌다 (2026-09-16)

가장 성적 좋았던 조합(직접 예측·180일 학습)에 손실함수만 바꿔 봤다. M5 대회 상위권 솔루션 다수가
`objective='tweedie'`(판매량처럼 0이 많고 오른쪽으로 치우친 분포에 적합)를 썼다는 게 잘 알려진
관행이라 기대했지만, 결과는 **0.9374로 기존 L2 손실(0.9200)보다 오히려 나빴다**
(`tweedie_variance_power=1.1`, `n_estimators=150`, 나머지 동일).

| 모델 | 손실함수 | 학습 데이터 | OVERALL |
|---|---|---|---:|
| seasonal-naive | - | - | **0.9128** |
| LightGBM 직접 | L2(기본) | 180일 | 0.9200 |
| LightGBM 직접 | Tweedie | 180일 | 0.9374 |
| LightGBM 직접 | L2(기본) | 전체 5.2년 | 0.9386 |
| LightGBM 재귀 | L2(기본) | 전체 5.2년 | 0.9601 |

**결론(이번 라운드 종료)**: 이번 특징 세트·이 정도 튜닝 범위(objective 1종·학습 윈도우 2종·
n_estimators 100~200) 안에서는 **seasonal-naive(0.9128)가 시도한 5가지 LightGBM 조합을 전부
이긴다.** Tweedie가 안 통한 것도 정직하게 남긴다 — `tweedie_variance_power`를 더 탐색하거나
learning_rate·num_leaves를 같이 조정하면 다를 수 있지만, 이번 세션에서는 여기서 실험을 접는다.
데이터가 많을수록, 모델이 복잡할수록, "유명한 트릭"을 쓸수록 좋다는 직관이 전부 깨진 것 자체가
이 프로젝트 시리즈의 일관된 결론이다.

### 자체계산 WRMSSE(0.9128)와 공식 Kaggle 채점(0.86967) 불일치 원인 규명 — 해결 (2026-09-17)

`weights.py`(레벨 내 가중치)는 확인 결과 문제가 없었다 — 매출 0인 시리즈는 `totals=0`이라
`weight = 0/grand_total = 0`으로 이미 자동 제외되고 있었다. 실제 원인은 `evaluate.py::rmsse()`의
**스케일(분모) 계산**이었다. 공식 M5 정의는 "그 시리즈가 실제로 팔리기 시작한 날(첫 non-zero)"부터만
naive 1-step 오차를 계산하는데, 이 구현은 `sales_train_evaluation.csv`가 d_1(2011-01-29)부터
빽빽하게 채워둔 **출시 전 0-패딩 구간**을 그대로 diff에 포함시켰다. 출시 전 0들은 diff가 0이라
분모(평균 제곱오차)를 인위적으로 낮추고, 결과적으로 RMSSE(분자/분모)를 과대평가한다 — 특히
품목 단위(item·item_store)처럼 출시 시점이 제각각인 하위 레벨에서 영향이 크다.

`rmsse()`에 `nonzero_idx = np.flatnonzero(train_actuals); train_actuals = train_actuals[nonzero_idx[0]:]`
한 줄을 추가해 첫 non-zero 이전 구간을 잘라내고, naive 베이스라인으로 재계산했다.

| | 자체계산(수정 전) | 자체계산(수정 후) | 공식 Kaggle Public |
|---|---:|---:|---:|
| OVERALL | 0.9128 | **0.8697007** | 0.86967 |

수정 후 값이 공식 채점과 소수점 4자리까지 사실상 일치(차이 0.00003, 남은 잔차는 부동소수점/반올림
수준으로 추정) — **불일치의 진짜 원인은 가중치가 아니라 스케일 계산의 리딩제로였다는 것을 확정**했다.
레벨별로 보면 상위 레벨(total 0.7514, 변화 없음 — 애초에 출시 전 0이 없어 영향 안 받음)은 그대로고,
하위 레벨(item 1.0322·item_store 1.1004, 수정 전 각각 1.0283·1.3051 근사 규모)이 크게 움직였다 —
가설(하위 레벨일수록 영향 크다)과 방향이 일치한다.

**회귀 검증**: 리딩제로가 없는 기존 손계산 테스트(`test_rmsse_hand_computed_example` 등)는 그대로
통과, 리딩제로 트리밍 자체를 검증하는 테스트 2개를 신규 추가(`test_rmsse_trims_leading_zeros_before_launch`·
`test_rmsse_leading_zeros_inflate_score_when_not_trimmed_would_differ`) — 총 43개 테스트 전부 통과.

**정직한 범위(갱신, 2026-09-17)**: 위 문단은 "재실행해서 확인하지 않았다"고 남겼었는데, 이어지는
세션에서 2개 조합을 실제로 재학습·재평가했다(아래 표). 나머지 2개(직접+전체이력·Tweedie)는
재실행하지 않았다 — 그대로 이 밑 절 참고.

### 리딩제로 수정 후 재평가 — 다섯 조합 전부 완료, 순위·결론 안 바뀜 (2026-09-17~18)

다섯 조합(재귀·직접+180일·직접+전체이력·Tweedie 전부)을 고친 `evaluate.py`로 재학습·예측·채점
완료했다. 재귀·직접+180일은 09-17 세션에서, 나머지 둘(직접+전체이력·Tweedie)은 자율모드 fork가
재학습까지는 끝냈지만(예측 parquet 저장, 09-17 밤) 채점·README 반영 전에 중단돼 09-18에
`scripts_score_cached_preds.py`(재학습 없이 캐시된 예측만 로드해 채점)로 마무리했다. 예측 결과는
`artifacts/pred_{recursive,direct180,direct_fullhistory,tweedie}.parquet`로 전부 캐시돼 있어
다음엔 재학습 없이 바로 재평가 가능하다.

| 모델 | 수정 전(버그) | 수정 후(전부 재실행 확인) |
|---|---:|---:|
| seasonal-naive | 0.9128 | **0.8697007** |
| LightGBM 직접+180일(L2, 최고 기록) | 0.9200 | **0.8984186** |
| LightGBM 직접+180일(Tweedie) | 0.9374 | **0.9039398** |
| LightGBM 직접+전체이력(L2) | 0.9386 | **0.9212378** |
| LightGBM 재귀+전체이력 | 0.9601 | **0.9255814** |

**순위는 완전히 그대로다**: naive < 직접+180일(L2) < Tweedie < 직접+전체이력 < 재귀 — 버그
수정 전후로 다섯 조합의 상대 순위가 단 하나도 안 바뀌었다. naive를 이긴 조합도 없다(전부 짐).
다만 격차는 전반적으로 벌어졌다 — naive와 최선 조합(직접+180일) 차이가 0.72%p(버그 있던 값
기준)에서 2.87%p(수정 후)로 커졌다. 레벨별 패턴(세분화 레벨은 LightGBM 우위, 상위 레벨은
naive 우위)도 다섯 조합 전부에서 유지된다.

**이 결과가 의미하는 것**: 리딩제로 버그는 절대 점수를 전부 낮췄지만(모든 모델이 좋아 보이게
만듦), 모델 간 상대적 우열은 전혀 안 바꿨다 — 즉 이 프로젝트의 핵심 결론("이 특징 세트·이 튜닝
범위에서는 naive가 다섯 가지 LightGBM 조합을 전부 이긴다")은 버그와 무관하게 처음부터 맞는
결론이었다. 버그가 결론을 뒤집을 수도 있었다는 우려가 있었기에, 이걸 실제로 확인한 것 자체가
이번 재평가의 가치다.

## 교체 기록

1. **재귀적 다단계 예측 → 지평선별 직접(non-recursive multi-horizon) 예측.** 재귀 방식이
   상위 집계 레벨에서 naive에게 지는 걸 보고(0.8555 vs naive 0.7514), 오차 누적을 의심해
   28개 지평선 각각 별도 모델로 바꿨다. 상위 레벨이 실제로 개선됐지만(0.8089) naive를 완전히
   이기지는 못했다 — 가설의 방향은 맞았지만 문제의 전부는 아니었다.
2. **직접 모델 학습 구간 180일 → 전체 5.2년, 다시 180일이 나음으로 확인.** 데이터를 더 주면
   나아질 거라 예상하고 전체 이력으로 재학습했으나 오히려 나빠졌다(0.9200→0.9386). "많을수록
   좋다"는 가정을 실측으로 기각했다 — 최종적으로 세 LightGBM 변형 중 어느 것도 naive를
   못 이겼다.

## 에러 대처 기록

**OOM(메모리 부족)으로 전체 이력 직접 모델 학습이 죽음 (2026-09-16).** `train_direct_multihorizon`이
28개 지평선을 반복하며 매번 5,900만 행 특징 프레임을 새로 만들었는데, 두 가지가 겹쳐 메모리를
과하게 먹었다: ① `long_df`에 특징공학에 안 쓰는 넓은 컬럼(문자열 `d`, `wm_yr_wk`)까지 실려 있었고
(문자열 컬럼은 object dtype이라 5,900만 행에서 특히 비쌈), ② 반복 사이에 이전 `feat`를 명시적으로
비우지 않아 GC가 늦게 돌 여지가 있었다. `data_loader.py`에서 병합 후 안 쓰는 컬럼을 드롭하고
(`long_df` 메모리 5.7GB→2.0GB), `models_gbm.py`에 반복마다 `del feat; gc.collect()`를 추가해
해결했다. **수정이 계산 결과를 바꾸지 않았는지**는 naive 베이스라인 WRMSSE(0.9128)를 수정 전후로
다시 돌려 정확히 같은 값이 나오는 것으로 확인했다 — 성능 최적화가 조용히 정답을 바꾸는 사고를
막는 회귀 검증 습관.

**긴 재학습을 백그라운드로 맡긴 자율모드 세션이 결과 반영 전에 끊김 (2026-09-17 밤).** 직접+전체
이력·Tweedie 재학습(각 48분·16분 예상)을 자율모드 fork에 맡겼는데, fork가 학습·예측까지는 끝내
`artifacts/pred_direct_fullhistory.parquet`·`pred_tweedie.parquet`을 저장했지만, 마지막 채점과
README 반영 단계 전에 세션이 끊겼다(원인 불명 — 프로세스 종료로 추정, 재현 안 함). **다음 세션에서
"완료됐다"는 알림을 못 받았다고 결과가 없다고 단정하지 않고, 먼저 `artifacts/`에 실제로 예측
파일이 저장돼 있는지부터 확인**해 재학습 없이 채점만 마무리했다(`scripts_score_cached_preds.py`) —
긴 배치 작업은 중간 산출물을 디스크에 캐시해두는 습관이 이번처럼 세션이 끊겨도 작업을 통째로
날리지 않게 해준다는 걸 실전에서 확인했다.

    실제로 두 가지를 확인해서 막혔다(추측 아니라 명령 실행 결과):
    - **파일 크기**: Cloudflare Pages 정적 자산은 파일당 25 MiB 상한(공식 문서 확인).
      `forecast_store.json`(39MB)은 그대로 못 올린다 → `scripts_shard_forecast_store.py`로
      주(state) 3개 샤드로 분리(`artifacts/cf_shards/forecast_{CA,TX,WI}.json`,
      13.4MB/10.0MB/10.0MB — 전부 상한 이내로 확인). 메타데이터(모델·예측일·이벤트·SNAP)를
      각 샤드에 중복 포함해 샤드 하나만 받아도 완결된 응답이 되게 함.
    - **인증/버전 차단(실제 실행해서 확인)**: `npx wrangler@latest`는 "Wrangler requires at least
      Node.js v22.0.0. You are using v20.19.4."로 즉시 실패(이 환경 Node는 20.19.4). Node 20과
      호환되는 `wrangler@3`으로 내리니 실행은 되지만 `wrangler pages project list`가
      "In a non-interactive environment, it's necessary to set a CLOUDFLARE_API_TOKEN
      environment variable"로 실패 — **이 환경에 Cloudflare 계정도 API 토큰도 없다.**
      로그인은 브라우저 OAuth라 비대화형 환경에서 대행 불가.
    - **더 근본적인 문제(설계 재검토 필요)**: 설사 배포된다 해도 Cloudflare Pages/Workers는
      정적 자산 + JS/Wasm만 지원한다 — `m5fc/agent.py`(LangGraph, Python)는 그 위에서 못 돈다.
      "정적 프론트 + 사전계산 JSON"까지는 되지만, **살아있는 LLM 에이전트 질의응답**을 Cloudflare
      에서 재현하려면 `agent_tools.py`의 순수 함수 로직(파싱→필터→집계)을 JS로 다시 짜야 한다 —
      이번 세션엔 손대지 않았다(검증 안 된 재작성보다 정직한 기록을 우선).
    - **다음 세션에 사용자가 준비할 것**: ① Cloudflare 계정 생성 + Pages/Workers 권한 API 토큰
      발급 → `CLOUDFLARE_API_TOKEN` 환경변수로 제공(또는 Node를 22+로 올려 `wrangler login`
      대화형 로그인). ② 그래도 라이브 에이전트까지 원하면 "JS로 조회 로직 재구현" vs
      "이미 검증된 Hugging Face Spaces 패턴(Gradio, 이 프로젝트 다른 데모들과 동일)으로 Python
      그대로 배포" 중 하나를 사용자가 먼저 결정 — Cloudflare는 정적 데모(사전계산 결과 조회만,
      LLM 없음)에는 맞지만 이 프로젝트의 핵심인 "에이전트가 근거를 들어 답변한다"에는 HF Spaces가
      아키텍처상 더 맞는다는 것이 이번 조사의 결론이다.

## 정직한 범위

- **(2026-09-18 최종 확정) 다섯 가지 LightGBM 조합 전부 리딩제로 수정 후에도 재실행 확인
  완료 — seasonal-naive(0.8697)를 하나도 못 이겼고 순위도 안 바뀌었다**: 직접+180일(L2) 0.8984 <
  Tweedie 0.9039 < 직접+전체이력 0.9212 < 재귀 0.9256. 이번 특징 세트(lag/rolling/가격/캘린더)와
  이 정도 하이퍼파라미터 탐색 범위(n_estimators 100~200, learning_rate·num_leaves 고정) 안에서
  나온 결론이다. 버그 있던 공식 기준 값(0.9200/0.9374/0.9386/0.9601)은 더 이상 인용하지 않는다.
- 대회는 이미 6년 전 종료되어(2020년) 공식 Private LB에는 Late Submission으로만 채점된다 —
  실시간 순위 경쟁이 아니라 "당시 참가자들 기준으로 내 모델이 어느 위치인가"를 보는 용도.
- **(2026-09-17 해소)** 자체 계산 WRMSSE(0.9128)와 공식 Kaggle 채점(Public 0.86967) 불일치는
  `rmsse()` 스케일 계산의 리딩제로 트리밍 누락이 원인이었고, 수정 후 0.8697007로 공식값과 사실상
  일치함을 확인했다(위 "성능 비교" 절 참조). 재귀·직접+180일 두 조합은 재실행해 순위 불변·격차
  확대를 확인했고(위), 직접+전체이력·Tweedie 두 조합은 재실행 전이다.
- **에이전트는 아직 실제 LLM으로 라이브 테스트하지 못했다** — 이 환경에 Gemini/Anthropic/OpenAI
  키가 하나도 없어서, 도구 체인(파싱→조회→집계)까지는 실데이터로 검증했지만 마지막 "LLM이
  자연스러운 문장으로 서술하는" 단계는 결정론적 템플릿으로만 확인했다. 키가 생기면
  `m5fc/agent_llm.py`가 자동으로 실제 LLM 경로를 탄다.
- **(2026-09-17 부분 해소)** `store_id`·`dept_id`는 이제 자유 발화를 인식한다("텍사스 3번 매장"→
  `TX_3`, "식품 1번 부서"→`FOODS_1`, "CA_2"류 직접 코드도 지원) — 실데이터 `forecast_store.json`

  존재하지 않는 조합(예: WI에 4번 매장, HOUSEHOLD에 3번 부서)은 `VALID_STORES`/`VALID_DEPTS`로
  걸러 지어내지 않는다(회귀 테스트 6개 추가, `test_agent.py`). **item_id(품목 3,049개)의 자유
